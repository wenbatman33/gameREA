# New local feature generator

`generateFeatureRound({totalBet, random, weights, mode, config, jackpotPools})` returns `{stages,totalWinnings,featureSummary}`. Modes: `ordinary`, `freeGame`, `superFreeGame`, `superMainGame`. Fill the wallet operation's `spinId` on every stage in the service adapter; the generator never reads or writes a wallet, storage, network, or captured round.

Public displayed parts: normal paytable/bet divisor20, scatter4/5/6 pay60/100/2000, 2–500x multiplier range and sum at end of a winning cascade chain, free15 and retrigger+5 with ordinary max100, golden action`freeSpin`, totem triples pay5, purchase costs supplied by FeatureDefinitions, guaranteed500 ball for superMainGame. `roundWinnings` is the current subround cumulative amount; `totalWinnings` is the operation cumulative amount. Final empty-win stage contains multiplier adjustment and scatter payout. All monetary arithmetic uses integer cents after each displayed base payout rounding.

**This is not original server mathematics or recovered RTP.** FeatureDefaults explicitly exposes local symbol probabilities, multiplier-value distribution, double-on-upgrade steps, lock duration, split copies/targeting, fixed locked-cell gravity, golden cap100 (must be15+5k), super rounds3, cumulative multiplier boundary interpretation and rounding. Golden original cap and super original round count are unknown. Results and full chosen config are recorded in featureSummary. No payout cap is invented; unsafe monetary overflow or nonterminating generation throws before a wallet may debit.

Each feature stages array is complete and deterministic for the supplied RNG sequence, but fresh RNG produces fresh symbols. `maxCascades` and `maxStages` reject the entire operation instead of truncating. Free trigger introductions are newly generated normal boards conditioned to contain four scatters and no unaccounted normal win. Pathological RNG fails after1000 initialization attempts. Ordinary free100 cap stops creating qualifying retriggers after the last authorized+5 to match the UI's unconditional scatter animation.

`timesSymbols` represents the current view; male split targets are currently removed winning cells, materialized by the original clone animation between removal and gravity. The next view contains those identical-value copies. Position transforms omit unchanged symbols and execute bottom-up without overwriting an unmoved source. Locked positions are barriers in the explicitly local gravity model; locks decrement only at subround boundaries and expire before the next board.

`config.jackpotSymbolCount` is0 or2..5, selected exactly once by the service/JackpotRules. FeatureRules inserts real symbol14 into the generated board, preserves the count, and marks the first actual-JP subround's empty-win terminal `isJp`, with its absolute array index in `featureSummary.jpStageIndex`. This phase may precede a free introduction or lie within a purchased free/super sequence; its actual board still contains the selected JP count. It does not consume pools or add a JP award: the service must add the settled pool amount once to the operation total, the JP phase roundWinnings, and that and all subsequent stage totalWinnings. A separate explicitly local frontend compatibility flow must present JP before resuming the original feature route; ordinary original flow alone does not handle JP inside free/super. The original popup reads totalWinnings.

Developer-only scenarios: multiplier, freeGame, free-retrigger, superFreeGame, split, lock, superMainGame. These condition freshly generated symbols; no canned responses. `jackpot-*` selection still requires the service's explicit count. The service, not this pure generator, must restrict scenario access to an explicitly chosen debug test wallet.

Validation: `node --experimental-vm-modules tools/seth-recovery/test-feature-rules.mjs` runs17 contracts directly against the Creator source. This covers a separate cent oracle, long100-round termination, newly varied boards, clone/lock identities, exact source-map replay, rejection paths and JP count preservation. It does **not** establish that original Creator feature animations complete. Each real UI route still requires independent verification.

## Multiplier application boundary correction

The current subround must have both a base win and at least one multiplier ball to apply the accumulated-plus-current multiplier. A winning subround with an already accumulated total but **no current multiplier ball** receives the base amount only, and preserves the accumulated total for a later qualifying board. This corrects an earlier overbroad local interpretation. Evidence: displayed English/traditional-Chinese rules02 qualifies adding multiplier value with a win and a multiplier symbol; original `CreateNewStopSpinFlowCmd.ShowWinFlow` requires previous wins, an empty-win terminal and current `timesSymbols.length` to enter SHOW_TIMES_MOVING; original EffectsView sends MERGE_WIN_AMOUNT from the last current ball. rules03's formula alone does not establish applying saved multipliers without a current ball. The independent cent oracle and a targeted generated test exercise at least five actual cumulative>0/no-ball winning subrounds.
